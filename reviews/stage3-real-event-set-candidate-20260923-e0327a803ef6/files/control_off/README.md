# Control sin observador del fallo de dominio

El [plan prospectivo](PLAN.json) reservó un sham completo sin observador para separar artefacto de captura y defecto previo del motor. El [recibo](full_sham_off_01/RESULT.json) reproduce el fallo del brazo con tap: 40 ms de preparación, 79 ms de ensayo completos, y al siguiente paso `accepted event state outside domain` en índice 28296 con valor `1.0000000000000002`. La [comparación](COMPARE_PREFIX.json), [código](compare_prefix.py), verificó igualdad bit a bit de **todos los campos de las 119 observaciones previas** y coincidencia del recibo numérico de fallo. No hubo una corrida válida a 320 o 400 ms.

Una [prueba aritmética CPU](ROUND_OFF_FIXTURE.json), [fuente](fixture_roundoff.py), muestra que la fórmula del productor de saltos y la del proyector pueden dar 1+1 ulp aunque la identidad real sea 1 (1.395 de 200.000 casos sintéticos preacotados). Una [prueba GPU](CUDA_PORT_FIXTURE.json), [fuente](fixture_cuda_port.py), del kernel real con saltos exactamente al final del bloque no reprodujo el exceso en 100.000 casos. Los dos fixtures prueban alcances distintos; ninguno contiene el evento real de KCa'b'-ap2_R. Por ello aún no se atribuye causalmente el fallo a redondeo, rigidez o un salto incorrecto.

Rivales de ingeniería: **A**, artefacto del tap, refutado para este fallo por el control exacto; **B**, representación del evento y redondeo de la superposición, plausible pero no identificado en la mosca; **C**, dinámica rígida/recurrente, todavía sin evidencia. El siguiente paso justificado es capturar dentro del primer fallo los valores `q`, `tau`, tiempos y saltos de esa KC antes del rollback, junto al estado fino intentado, sin publicar el propietario fallido como checkpoint reanudable. No se han tocado cotas, ganancias, pesos ni conectividad.
